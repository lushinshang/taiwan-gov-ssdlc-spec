資訊系統安全開發與資安檢測作業規範

依據《資通安全管理法》第9條及其施行細則、《資通系統防護基準》及工程會採購契約範本，專門規範受託廠商於「程式開發實作」、「功能與系統測試」至「資訊安全技術檢測（SAST/DAST/滲透測試）」之執行程序、安全標準與交付審查

規範範疇：安全程式設計 ➔ 軟體供應鏈(SBOM) ➔ 白箱源碼掃描 ➔ 黑箱弱掃 ➔ 滲透測試 文件責任：機關資通安全主管與承辦工程師

零、 廠商遵循總則與法遵拘束力說明

本規範為本專案委外採購契約之不可分割技術規範。受託廠商於進行本專案之程式撰寫、功能整合、測試與資安檢測期間，必須嚴格依照本程序書明定之順序推進。上一程序之安全控制與檢測報告未經機關審查核可，廠商不得逕行提報系統驗收或部署上線。

⚖️ 法遵依據與法律拘束力宣告（契約履約強制力）：
  • 法源依據一（母法委外選任與監督義務）： 依 《資通安全管理法》第 9 條及施行細則第 7 條 規定，機關委外辦理資通系統之建置、維運或資通服務，應選任具備資安防護能力之廠商，並於契約明訂監督與稽核權；受託者辦理客製化開發必須提供安全性檢測證明。
  • 法源依據二（防護基準法定要求）： 依 《資通安全責任等級分級辦法》附表十「資通系統防護基準」 規定，各機關依附表九分級後，系統開發與維護構面明文強制要求執行原始碼檢測、弱點掃描及滲透測試，且中高風險弱點必須修補完成。
  • 契約履約依據（驗收前置條件）： 依 行政院公共工程委員會《資訊服務採購契約範本》 第 8 條履約管理、第 15 條及第 16 條驗收規定，受託廠商未出具合格之資安檢測報告並修復中高風險漏洞前，機關依契約約定得暫停付款或判定驗收不合格。

貳、 委外廠商核心作業程序（管理啟動 ➔ 開發 ➔ 測試 ➔ 資安檢測）

廠商專案主管、架構師、開發工程師與品保檢測團隊，必須嚴格依照下列程序循序執行：

專案管理先行程序：專案執行計畫、工作分解 (WBS)、團隊權責 (RACI) 與風險管理 (Risk Management) PMP MANAGEMENT
📌 契約法遵與專案分工強制要求：

依據工程會《資訊服務採購契約範本》第 8 條第 2 款第 1 目規定，廠商應於決標後 20 日內提報《專案工作執行計畫書》。本專案特別要求該計畫書必須具備結構化之 WBS、RACI 與 風險管理計畫（Risk Register），以落實資安法之職能分工（SoD）與風險預警機制：

  • 工作分解結構（WBS, Work Breakdown Structure）： 廠商必須將整個軟體開發、組態建置、第三方套件清點（SBOM）、單元測試、整合測試、原始碼掃描（SAST）、弱點掃描（DAST）與滲透測試修補，拆解至可獨立驗收與指派負責人之第三層以上 WBS 工作包（Work Packages）。
  • 責任分工矩陣（RACI Matrix）： 必須明確界定每一項資安工作之角色： R（Responsible 執行者）、 A（Accountable 當責者/最終簽核PM）、 C（Consulted 諮詢者/資安架構師）、 I（Informed 知會者/機關承辦）。 嚴格杜絕「開發兼檢測」、「自己掃描自己審查」等違反職能分工（Separation of Duties）之弊病。
  • 專案與資安風險管理機制（Risk Management & Risk Register）： 廠商必須建立專案風險登錄表（Risk Register），識別並預防三大核心風險構面：
    • 時程風險：資安檢測（SAST/DAST）掃描出大量中高風險漏洞，導致修補複測時程嚴重延誤交付。廠商應明訂預備緩衝期（Buffer）與資安技術專家支援機制。
    • 技術與供應鏈風險：關鍵第三方開源套件突發零日漏洞（0-Day）、套件過時無法修補或受大陸廠牌管制衝擊之替代方案。
    • 人因與資安事件風險：專案成員流動導致機敏金鑰外洩、或開發測試環境遭受勒索病毒感染之應變處置。
  • 開發過程突發事故應變計畫（Incident Response Plan）： 依官方指引規定，開發過程中若發生原始碼外洩、開發測試伺服器遭入侵、或第三方套件爆發重大供應鏈威脅時，廠商必須啟動事故應變程序：
    • 1 小時緊急通報時效：依採購契約規範，廠商知悉事件後必須於 1 小時內通報機關，並於 4 小時內提報初步隔離與損害控制方案。
    • 7x24 緊急聯絡窗口：廠商團隊必須明訂具有授權之緊急資安聯絡人，確保突發資安事故可即時啟動應變小組。
    • 事故復原與影響分析報告：事件排除後 72 小時內提送完整事故根本原因分析（RCA）及防範再發之代碼修補改善報告。
📑 依據法源與交付標準：
• 契約依據：工程會《資訊服務採購契約範本》第8條履約管理與資安事件通報條款。
• 官方指引：《安全軟體發展流程指引》 第 28 頁「事故應變計畫」與第 63 頁「威脅建模與風險消除對策」。
• 審查交付物：《專案工作執行計畫書》（內含 WBS 時程甘特圖、RACI 資安責任分工表、風險登錄表 Risk Register 與 突發事故應變程序書）。
程序一：安全程式開發實作作業（Secure Coding & Supply Chain） PROCEDURE 01
🛠️ 1.1 安全程式碼撰寫強制要求（全面對齊最新 OWASP Top 10）
💡 國際標準動態：OWASP 已正式發布第八代旗艦版本 OWASP Top 10:2025，特別將「軟體供應鏈失效（A03）」與「例外處理不當（A10）」列為獨立風險，並將 SSRF 收編至「權限控制失效（A01）」。本專案要求全面對齊最新版本防禦控制：
  • 徹底根絕注入弱點（A05:2025 Injection，含 SQLi / XSS）： 所有資料庫存取必須全面採用參數化查詢（Prepared Statements / Parameterized Queries）或經安全驗證之 ORM 框架，嚴格禁止使用字串拼接（String Concatenation）組裝 SQL 語法；所有前端輸出至瀏覽器前必須執行上下文敏感之輸出編碼（Output Encoding）。
  • 權限控制與伺服端請求防偽（A01:2025 Broken Access Control，含 SSRF）： 嚴格落實角色型存取控制（RBAC），且權限檢驗邏輯必須 100% 在伺服器端（Server-Side）執行，嚴禁依賴前端參數控制；對外連線請求必須建立 URL 白名單過濾，防範伺服端請求偽造（SSRF）向內網探測。
  • 安全組態加固（A02:2025 Security Misconfiguration）： Web 系統必須依官方指引啟用安全標頭（`Strict-Transport-Security`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN` 及 `Content-Security-Policy`），正式環境強制關閉除錯模式（Debug Mode）與多餘預設端點。
  • 密碼學與機敏資訊保護（A04:2025 Cryptographic Failures）： 嚴禁在原始碼、組態檔或 Git 紀錄中硬編碼（Hard-coded）帳號密碼、API 金鑰或憑證。使用者密碼儲存必須採用強固雜湊演算法加鹽（Salted Hash，如 PBKDF2、bcrypt 或 Argon2id），嚴禁使用 MD5 或 SHA-1。
  • 例外與錯誤狀況安全處理（A10:2025 Mishandling of Exceptional Conditions）： 所有 API 與控制器必須建立健全之全域例外捕捉機制，錯誤訊息嚴禁將資料庫錯誤碼、框架底層堆疊追蹤資訊（Stack Trace）回傳給前端使用者。
📦 1.2 軟體供應鏈安全與產出 SBOM 清單
  • 第三方開源套件管制： 廠商必須於開發階段建立軟體成分分析（SCA），使用開源工具（如 `Syft`、`Trivy`）掃描並產出標準格式（SPDX 或 CycloneDX）之軟體物料清單（SBOM），比對國家 NVD / OSV 資料庫，確認無重大已知 CVE 弱點。
  • 禁止使用大陸廠牌資通訊產品： 依行政院政策規定，廠商交付之軟體套件、第三方相依模組或開發環境，一律嚴格禁止採用大陸廠牌資通訊產品或具安全疑慮之模組。
📑 本程序依據文件與廠商應交付審查物：
1. 依據文件：《Web 應用程式安全參考指引 v3.2》 及 《HTTP 安全標頭防護設定》。
2. 廠商應交付審查物：
  • 已填報勾稽完成之 《附件1 Web應用程式安全查檢表.pdf》。
  • 系統相依套件清冊與標準 SBOM 檔案（SPDX / CycloneDX json）。
  • 廠商具結之《無大陸廠牌資通訊產品切結書》。
程序二：功能驗證與系統整合測試作業（Functional & Integration Testing） PROCEDURE 02
🧪 2.1 測試環境與安全功能驗證
  • 測試環境獨立隔離： 系統測試作業必須在獨立之測試環境進行，測試環境應與開發環境及未來正式營運環境實體或邏輯隔離。嚴禁在測試環境中使用未去識別化之真實民眾個資。
  • 安全邊界與異常輸入測試： 測試案例必須包含負向測試（Negative Testing）與極限邊界測試，包含超長字串、特殊符號、SQL 語法注入、非預期型態之輸入驗證，確認系統具備適當之例外處理（Exception Handling），不會洩漏系統堆疊追蹤資訊（Stack Trace）或伺服器敏感情資。
  • 存取控制邏輯測試： 驗證跨使用者之垂直越權（一般使用者試圖呼叫管理員 API）與水平越權（使用者 A 竄改參數存取使用者 B 之資料），確認 RBAC 授權機制在每支 API 均完整生效。
💾 2.2 開發與測試過程「資料／數據及儲存媒體（磁碟）」安全管理與生命週期規範
  • 測試資料選取與嚴禁真實個資（Data Sanitization）： 依官方《安全軟體發展流程指引》第 118-119 頁規定，測試資料必須謹慎選取，嚴禁直接複製正式環境之真實民眾個資、未去識別化資料作為開發測試之用。若因特殊業務驗證必須使用正式資料副本，必須經機關獨立專案核准，並落實遮罩、混淆（Masking）或雜湊去識別化，比照正式環境存取控制，測試完畢立即自開發磁碟中抹除。
  • 靜態儲存加密（Data-at-Rest Encryption）： 依《資通系統防護基準》第 4 頁規定，含有機密性、敏感資料之測試資料庫與開發暫存區，其磁碟區塊或資料庫欄位必須採用強固加密機制儲存（如 AES-256 全磁碟加密 FDE 或透明資料加密 TDE）。
  • 磁碟與儲存媒體生命週期清除作業（Media Sanitization）： 依官方指引第 52 頁「媒體清除規範」及工程會採購契約規定，專案開發完成、伺服器汰除、租賃主機退租或硬碟送修前，必須對儲存過專案程式碼與業務資料之磁碟執行安全清除（DoD 5220.22-M 或 NIST SP 800-88 清除標準），消磁或重複覆寫銷毀，並產出《儲存媒體資料抹除銷毀證明切結書》，嚴禁未經抹除直接拋棄或移作他用。
📑 本程序依據文件與廠商應交付審查物：
1. 依據法規：《附表十 資通系統防護基準》 第 4 頁「資料儲存」與「環境區隔」規定。
2. 指引出處：《安全軟體發展流程指引》 第 52 頁「媒體清除」及第 118-119 頁「測試資料保護」。
3. 廠商應交付審查物：
  • 系統整合測試計畫書與安全功能測試案例（Test Cases）。
  • 測試資料去識別化與保護宣告書。
  • 專案結束時提送之《儲存媒體資料安全抹除銷毀紀錄切結書》。
程序三：資訊安全技術檢測與修補驗證作業（SAST / DAST / 滲透測試） PROCEDURE 03
🛡️ 3.1 原始碼安全檢測作業（SAST，白箱靜態檢測）
  • 適用等級與範圍：中防護等級及高防護等級系統強制實施。檢測範圍涵蓋專案開發之所有後端、前端原始碼及預存程序（Stored Procedures）。
  • 合格修補標準： 掃描報告中標註為「高風險（High / Critical）」與「中風險（Medium）」之漏洞，必須全數（100%）完成修補。若廠商主張特定項目為工具誤判（False Positive），必須檢附原始碼行號、上下文邏輯分析佐證，經機關資安人員審查核可後方得列入除外清單。
🌐 3.2 系統與應用程式弱點掃描作業（DAST，黑箱動態檢測）
  • 適用等級與範圍：所有資通系統（普、中、高）皆強制實施。包含作業系統主機、網頁伺服器（Web Server）、資料庫及 Web 應用程式對外服務埠口。
  • 合格修補標準： 所有掃描發現之中、高風險弱點必須於申報驗收前全數修復，並於修補後進行複測，出具修復後無中高風險漏洞之「複測合格報告」。
⚔️ 3.3 滲透測試作業（Penetration Testing，模擬黑客攻擊）
  • 適用等級與資格：中、高防護等級系統或提供民眾對外服務之核心系統強制實施。必須由持有公信力資安證照（如 OSCP、CEH、GWAPT 或同等實力）之資安測試人員執行。
  • 報告必備要件（拒收空泛報告）： 滲透測試報告必須具備：(1) 測試範疇與受測 IP/URL、(2) 弱點分類與 CVSS 3.1 評分、(3) 概念驗證（PoC）重現步驟與攻擊截圖、(4) 具體代碼修正或組態補強建議、(5) 修補後複測通過佐證。
📑 本程序依據文件與廠商應交付審查物：
1. 依據法規：《附表十 資通系統防護基準》 系統發展與維護構面、工程會契約範本第8條。
