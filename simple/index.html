🌱 第 0 章：觀念翻轉 — 資安不是找碴，是讓你準時下班

老實說，身為開發者，誰不曾暗自討厭過資安？

每次辛辛苦苦熬夜把功能刻完，PM 點頭、QA 測過，眼看著終於可以開心結案、準備去吃頓好料，資安團隊（或掃描工具）突然丟來一份幾十頁滿江紅的報告。上面滿滿看不懂的名詞（什麼 XSS、SQLi、BOLA），限期 3 天修補。心裡難免冒出一句：「這功能明明很順啊！誰沒事會這樣亂打？」

結果就是：被退件、修一堆看不懂的漏洞、加班救火，原本以為可以結案的專案硬是拖了兩個禮拜。這其實就是我們以前常走的冤枉路。

你不必成為神級駭客，更不用學著寫黑客工具。只要在寫程式的日常中養成 4 個肌肉記憶，資安檢測就能輕鬆一次過關。

📖 第 1 章：專有名詞白話字典 — 5 分鐘聽懂資安黑話

剛接觸資安，最怕看到一堆縮寫。記住以下這 5 個傳神的生活場景，你就能聽懂 90% 的資安對話：

🔍 SAST（靜態源碼檢測 / 白箱）
生活比喻：看食譜有沒有寫錯
工具直接讀你的 Source Code（不把程式跑起來），一行一行挑語法錯誤或危險寫法（例如把密碼直接寫死在程式裡）。就像編輯在審稿挑錯字。
💥 DAST（動態弱點掃描 / 黑箱）
生活比喻：在餐廳門口踹門、丟石頭試試窗戶會不會破
工具不看任何原始碼，把系統架起來後，模擬外部駭客對你的網址瘋狂狂發怪異 HTTP 封包，測試輸入框塞特殊符號會不會讓系統噴錯或吐出機密。
📦 SCA 與 SBOM（軟體組成分析與物料清單）
生活比喻：查食品成分標籤與過期原料
檢查專案 package.json 或 requirements.txt 引用的開源套件有沒有已知的 CVE 漏洞。SBOM 就是整張清楚的成分清單。
🕵️ 滲透測試（Penetration Testing）
生活比喻：請合格保全或白帽特警拿鐵撬實地搶劫演練
真人白帽駭客上陣！不靠死板工具，專門用人類的邏輯組合拳打系統漏洞（例如改 URL 偷看別人訂單、重複洗優惠券）。
🎭 去識別化（De-identification / 脫敏）
生活比喻：演員彩排時拿假道具代幣，不拿真鈔
把真實個資（身分證、信用卡）替換為假資料、打馬賽克或代幣化。測試環境絕對不能存放真實個資，外洩風險直接歸零。

🛡️ 第 2 章：寫 Code 實戰 — 開發者的防禦四部曲

這是工程師的核心基本功。以下四道門禁守好，90% 常見的高風險弱點立刻瓦解：

▲ 資訊圖解：輸入檢驗門、權限鑰匙、金庫密鑰、套件體檢站（防禦四道門禁）

門禁一：輸入驗證與過濾（永遠不信前端輸入）

前端的表單驗證只是 UX 防呆，擋不住 Postman 或駭客腳本。後端必須把任何外部傳入的資料（Query, Body, Header）都視為未爆彈！

❌ 玩火示範：字串拼接 SQL（門戶大開）
// 收到前端 user_name = "admin' --"
const sql = `SELECT * FROM users WHERE username = '${req.body.user_name}'`;
// 實際執行：SELECT * FROM users WHERE username = 'admin' --'
// 密碼檢查直接被 -- 註解掉，隨便就能登入！
✅ 安全防禦：參數化查詢 / ORM（指令與資料徹底分離）
// 1. Prepared Statement 寫法：資料永遠只當純資料處理
const sql = 'SELECT * FROM users WHERE username = ?';
await db.execute(sql, [req.body.user_name]);

// 2. ORM 寫法（例如 Prisma / TypeORM）：天然免疫
const user = await prisma.user.findUnique({
  where: { username: req.body.user_name }
});
⚠️ SSRF（伺服器端請求偽造）：別讓伺服器當駭客的免洗轉跳板！
如果系統有「輸入 URL 幫你抓網頁截圖或縮圖」的功能，駭客若輸入 http://169.254.169.254/latest/meta-data/（雲端金庫）或 http://127.0.0.1/admin，你的伺服器就會用自己的內網身份幫他抓出機密！
防禦秘訣：只允許 http/https 白名單網域，嚴格阻絕內網 IP（127.0.0.1、10.x、192.168.x、169.254.x）。

門禁二：認證與授權防漏（不只要登入，更要看是不是你的）

很多工程師以為只要檢查使用者有 JWT Token 就安全了，結果使用者把 URL 的 ?order_id=1001 改成 1002，立刻偷看到隔壁老王的訂單（水平越權 BOLA / IDOR）！

❌ 玩火示範：只查 ID，沒查是不是本人
// 雖然登入了，但只查 order_id，誰改網址誰就能看！
SELECT * FROM orders WHERE id = :order_id;
✅ 安全防禦：雙重鎖定（綁定登入者 ID）
// 永遠加上目前登入者的 user_id！
SELECT * FROM orders 
WHERE id = :order_id AND user_id = :current_login_user_id;

門禁三：機密憑證不落地（嚴禁 Hardcode Token 與密碼）

不管是 DB 密碼、AWS Key 還是第三方 API Token，絕對不能寫在程式碼裡 commit 進 Git！即使是 Private Repo，歷史紀錄也可能外洩。

正確做法：本機放 .env 並加入 .gitignore，正式環境使用環境變數（Environment Variables）注入。推薦團隊在 CI 加上 git-secrets 或 trufflehog 自動攔截！

門禁四：相依套件健康檢查（別把有毒的輪子裝進車裡）

現代軟體 80% 的程式碼來自第三方開源套件。日常養成習慣：

# Node.js 團隊：
npm audit
npm audit fix

# Python 團隊：
pip install pip-audit
pip-audit

🧪 第 3 章：測試實戰 — 千萬別把正式機資料直接 dump 回來！

很多團隊為了解 Bug 方便，最常做的危險動作就是直接下 pg_dump 或 mysqldump，把正式 DB 一鍵倒回測試機。結果外包筆電掉了、測試機忘記關公網，瞬間造成百萬筆個資外洩，踩中《個人資料保護法》與政府《附表十》的重大紅線！

▲ 資訊圖解：正式資料嚴禁直倒測試機！四道清洗工序讓測試環境零風險（直式與橫式自適應）

測試資料脫敏（去識別化）四大招

🟢 招式一：假資料生成器（首選推薦）
使用 faker-js 或 Python Faker 自動產生假中文姓名與台灣電話。從頭到尾沒碰真資料，外洩風險真正為零！
🟢 招式二：遮罩掩蓋（Masking）
身分證改為 A123***789、手機改為 0912***456。保留資料長度與格式，排版測試超方便。
🟡 招式三：雜湊替換（Hashing / Token）
不可逆轉成代碼，適合需要測試同一用戶唯一性與重複行為的測試場景。
🟡 招式四：隨機打散（Shuffling）
把資料庫的姓名與地址重新隨機洗牌配對。A 先生配上 B 小姐的地址，失去真實對應意義。

測試時多測測「壞蛋路徑」（Negative Testing）

測試別只測正常人會怎麼按，多測三種壞人亂輸的情境：

  • 長度超大：只能填 50 字的欄位，直接塞 10 萬字進去，看會不會把記憶體灌爆當機（DoS）。
  • 特殊字元：輸入 ' " < > ; \0，看系統會不會原封不動噴出資料庫錯誤（揭露系統架構）。
  • 邊界負數：電商購買數量故意輸入 -1，看會不會沒扣款反而「退錢」給你！

👾 第 4 章：驗收通關 — 拆解資安檢測三大魔王

面對驗收檢測不用慌，搞懂背後的原理與規則，你就能從容應對：

▲ 資訊圖解：白箱源碼檢測、黑箱弱點掃描、真人滲透測試通關全景

魔王一：白箱源碼檢測（Fortify / Checkmarx）

收到滿江紅報告怎麼辦？ 工具原則是「寧可錯殺，不願放過」。

  • 修補底線：High 與 Critical 風險必須全數歸零，這是標案基本驗收門檻。
  • 如何提出「誤判說明（False Positive）」？
    如果工具報 SQLi，但該變數其實只允許數字且你在前一層已經用 Regex ^\d+$ 鎖死，這就是誤判。
    千萬不要只寫「這不會發生」！ 請畫出資料流、標註防護代碼行號、具體說明駭客無法注入的理由，審查員才會爽快簽核。

魔王二：動態弱點掃描（AppScan / WebInspect / ZAP）

黑箱掃描前，團隊務必準備妥當：

  1. 提供足夠權限的測試帳號（會員與管理員各一組）。
  2. 測試環境暫時將掃描機 IP 放行，避免 WAF 擋住：如果防護沒關，掃描機被封鎖會跑出「0 漏洞」的假象，驗收時會被退件重測！
  3. 提供 OpenAPI / Swagger 文件：前後端分離時，爬蟲爬不到 API，必須主動提供端點規格。

魔王三：真人滲透測試（白帽攻防實戰）

白帽駭客專打「業務邏輯漏洞」（例如篡改價格、越權偷看資料、高頻發送封包搶優惠券）。

複測修補關鍵：
不要只修報告寫的那一行！駭客回報訂單 A 有越權，你要全面清查系統內所有訂單與查詢 API。修好後自己先開 Postman 改參數自測一次，確定回傳 403 Forbidden 再申請複測。
